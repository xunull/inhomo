# 规则缺口：按可注册域聚合兜底连接，做成「补规则」工作台

上一步（ADR 未记，见 T46 之后的「命中规则」面板）把 `rule` 维度接进了仪表盘，于是「兜底率 8.7%」第一次可见。但一个百分比答不了下一个问题：**该先给哪几个域名补规则**。本 ADR 记的就是那个页面。

## 背景事实（实测本机 7 天库快照，31.8 万条连接事件）

**「没命中任何规则」其实是三种状态**（见 `docs/mihomo-logs.md`）：

| 状态 | mihomo 日志 | 本机实测 | 补规则有用吗 |
|---|---|---|---|
| 落到末尾兜底规则 | `match Match` / `FINAL` | 27,610 条（8.69%） | 有用 |
| 连兜底规则都没有 | `doesn't match any rule` | 0 条 | 有用，且该补兜底 |
| 没走规则匹配 | 无 `match` 段 → `rule` 存空串 | 0 条 | **没用**（GLOBAL / specialProxy 下规则不生效） |

**聚合粒度**：27,610 条兜底连接落在 734 个 host 上，其中 91 个是 IP 字面量（9 IPv4 + 82 IPv6）。643 个域名 host 折叠到可注册域后剩 488 个。

**补 top-N 条规则能收掉多少兜底流量**（按连接数）：

| 补几条 | 累计收掉 |
|---|---|
| 1 | 21.4% |
| 3 | 47.9% |
| 5 | 63.6% |
| 10 | 83.2% |
| 20 | 91.0% |

**按连接数排序会埋掉大流量域名**：

| 目标 | 连接数 | 字节 | 连接数排名 | 字节排名 |
|---|---|---|---|---|
| 某更新分发域 | 8 | 1,047 MB | 104 | 3 |
| 某编辑器插件 CDN | 8 | 233 MB | 103 | 4 |
| 某遥测上报域 | 3,601 | 68 MB | 2 | 8 |

**字节关联的可靠性**：734 个兜底 host 里 **730 个只以兜底形式出现**（27,606 / 27,610 条 = 99.99%），故按 host 关联 `traffic` 表的字节是可信的。剩 4 个混有 `GeoIP(cn)`，且每个的兜底连接都恰好只有 1 条——是 GeoIP 数据就绪前的首连接，非真实混淆。

**长尾**：折叠后 115 个可注册域吃掉 26,440 条连接（97.4%）与 6,529 MB（99.8%）；其余 373 个合计仅 681 条、15 MB。

**时效**：505 个 host 在快照前 3 天起就没再兜底过（合计 2,076 条）；仍在近 24h 兜底的 183 个 host 占了 25,227 条（91%）。

## 决策

- **口径**：只收落到兜底规则与「连兜底都没有」两种；空串（GLOBAL / specialProxy）**排除**，但若切片内存在则在页顶明确提示其条数，不静默丢弃。
- **主体是「规则缺口」= 可注册域 + 其兜底连接汇总**，一行即一条待补规则；可展开看其下的具体子域，好在写宽泛规则前核实覆盖面。
- **折叠用 `x/net/publicsuffix` 的真 eTLD+1，不用「取末两段」**。末两段会把 `myblog.github.io` 算成 `github.io`（那是公共后缀），据此写出的 `DOMAIN-SUFFIX,github.io` 会误伤全部 GitHub Pages。为此把原先内联在 `tracker.Classify` 里的取值逻辑提成导出的 `tracker.RegistrableDomain`，两处共用同一实现。
- **连接数与字节两列常驻，默认按字节降序**。理由见上表：方向性判断（该不该补规则）更贴近流量而非连接数。字节列须标明来自抽样的流量记录（ADR-0008）。
- **不设门槛，改用「累计覆盖」列**：全部列出、按序累加，用户读到 95% 自会停手。这与 ADR-0013「宁可让用户看见证据不足，也不悄悄藏掉一行」以及 `/new` 的 `truncated` 标志同一原则。
- **自带时间窗，默认近 7 天**（档位 24h/7d/30d/全部），每行给出「最后兜底时间」。默认不取全时段，是因为早已补过规则的域名会一直留在历史里，把清单变成「历史上所有缺口的并集」。
- **规则片段带占位符**：`- DOMAIN-SUFFIX,example.com,<策略组>`，支持一键复制。inhomo **拿不到策略组名**——`detect.go` 的 `effectiveNode` 在解析时就把「分组名[真实节点|倍率]」里的分组名剥掉了（这是 CONTEXT「出境节点」术语的既有定义），历史数据也补不回来。
- **IP 字面量目标单独成区**，规则片段用 `IP-CIDR` 形态，不与域名混排。

## 取舍

- **与 ADR-0014 的正面冲突**：那份 ADR **明确否掉了 eTLD+1 折叠**（「仅降噪 30%，却要把计算从 SQL 拽到 Go 侧」），这里却采用它。取舍反转是因为**目的不同**：在新鲜度视图里折叠只是降噪手段，收益不抵成本；在这里折叠**是目标本身**——分流规则就写在可注册域这一级，不折叠等于没解决问题。同一技术在两个场景下结论相反，不是前后矛盾。
- **为什么排除空串而不是一并列出**：GLOBAL 模式下每条连接的 `rule` 都是空串，全收会让页面变成「建议你给所有域名补规则」，而补了不生效。这是唯一一处我们选择**排除**而非披露的数据，故用页顶提示补偿。
- **接受「最后兜底时间」不能区分两种沉寂**：一个域名不再兜底，可能是你补了规则，也可能只是最近没访问。库里能区分（看它近期有没有以别的规则出现），但 v1 只给时间、不做判定——实测该情形真实实例为 0，为它加一次跨表自连接不划算。
- **字节关联是按 host 而非按连接**：`traffic` 表没有 `rule` 列（见 ADR-0008 的两套数据集），只能按 host 关联。实测 99.99% 的兜底连接来自「只以兜底出现」的 host，故偏差可忽略；但这条前提得写在页面上。

## v1 不做

读 `/proxies` 拿策略组列表以生成完整规则行；把「已被规则接管」标出来；按 App 过滤缺口；导出为 rule-provider 文件；`IP-CIDR` 的掩码推断（v1 只给 `/32`、`/128` 单地址形态）。

## 延伸

「规则缺口」与 ADR-0013 的「应用通道」、ADR-0014 的「新增应用通道」构成三种互补的聚合主体：外发比问「这条通道传了多少」、新鲜度问「这条通道什么时候第一次出现」、规则缺口问「这个域名该不该有一条规则」。三者都拒绝把结论与其证据基础分开呈现——分别对应「采样覆盖率」「观测覆盖」「累计覆盖 + 抽样声明」。
